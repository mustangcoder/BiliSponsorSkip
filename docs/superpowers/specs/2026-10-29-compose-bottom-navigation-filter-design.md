# Compose 底部导航过滤兼容设计

## 意图

修复 B 站 9.15.0 通过远程实验启用 Compose 底部导航后，“隐藏底部会员购入口”和“隐藏底部发布按钮”开关仍开启，但按钮重新出现的问题。

## 根因

现有 `BottomMallTabHook` 只过滤旧链路中的 `tv.danmaku.bili.ui.main2.resource.x`。手机当前实际界面由 `WindowAwareComposeView` 渲染，数据来自 `HomeFrameViewModel.f526785i` 的 `Flow<List<Qo1.d>>`，因此旧 Hook 虽安装成功，却不再经过实际渲染数据。

手机实时证据同时确认：

- 安装包与本地 `live-bottom-filter-v2.apk` 完全一致。
- 模块总开关及两个底部入口开关均为开启状态。
- B 站接口仍下发稳定的 `tab_id`、`uri` 和发布类型标记，原有业务判断没有失效。
- 强制停止并重新启动后，旧 Hook 有安装日志，但没有过滤日志；当前界面层级明确为 Compose 底栏。

## 方案比较

### 方案 1：过滤 Compose 状态构造参数（已选）

Hook `Qo1.e` 的状态构造入口，在状态对象创建前过滤其第一项 `List<Qo1.d>`。优点是直接从数据源移除按钮，Compose 会按剩余数量重新布局，不留空白；同时可以保留旧链路以兼容未命中远程实验的设备。

### 方案 2：过滤接口到状态的转换函数

更接近原始接口数据，但转换函数位于更深的协程和 reducer 链路，混淆结构更多，升级风险和误伤范围更大。

### 方案 3：扫描 Compose 界面节点

只能隐藏渲染结果，容易留下空位；Compose 语义节点不是稳定的 Android View，也不适合作为主要方案。

## 设计

- 保留现有 `BottomMallTabHook`，继续支持旧版底栏。
- 新增 Compose 数据 Hook，寻找 `Qo1.e` 中首个参数为 `List` 的构造函数，并在构造前处理列表。
- 从每个 `Qo1.d` 读取其 `Po1.q` Tab 数据，映射为现有 `BottomTabIdentity`：
  - `Po1.q.h`：`tabId`
  - `Po1.q.c`：`uri`
  - `Qo1.d.o`：`isPublish`
- 继续复用 `shouldHideBottomTab`，不复制会员购和发布识别规则。
- 只在总开关及对应独立开关开启时过滤。
- 创建新的列表替换构造参数，不修改 B 站传入的原列表，避免不可变集合异常或影响其他消费者。
- 类、字段或构造函数不存在时失败开放，只记录诊断日志，不阻止 B 站启动。
- 成功过滤时记录 Compose 来源、移除数量和剩余数量，方便后续版本排查。

## 非目标

- 不修改现有设置项、默认值或设置同步协议。
- 不按“会员购”等可见文案扫描界面。
- 不处理其他 B 站版本的未知混淆结构。
- 不删除旧底栏 Hook。

## 验证

- 先增加失败测试，证明 Compose Tab 模型能按 `tabId`、`uri` 和 `isPublish` 过滤，并且原列表不被修改。
- 覆盖两个开关的独立组合、普通 Tab 保留、空值和不可识别对象失败开放。
- 运行全量单元测试及 Debug 构建。
- 打包 9.15.0 LSPatch APK，并核对内嵌模块、原包、版本和签名。
- 安装到当前手机，强制停止后重新启动；日志应出现 Compose 底栏过滤记录，界面只保留“首页、关注、我的”。
